IADT — Visão geral do fluxo (CLI e Worker SQS)

Descrição do que foi implementado: entradas, arquivos envolvidos, pipeline compartilhado e saída (disco ou fila JSON).

Visão geral

O mesmo núcleo de processamento — a função run() do orquestrador — atende dois modos:

  1. CLI (local): você passa o caminho de um arquivo no disco (imagem ou PDF).
  2. Worker SQS: um processo contínuo lê mensagens da fila de entrada, baixa o objeto do S3, executa o pipeline e publica um JSON na fila de saída.

A pasta domain/ concentra regras puras (contratos de mensagem, layout do relatório, parse por seções) sem dependência de boto3. A pasta adapters/aws/ concentra SQS e S3.

Fluxo 1 — CLI (arquivo local)

EtapaOnde
Entrada project/cli.py — argumento de linha de comando com o caminho do diagrama.
Orquestração project/orchestrator/pipeline.py — run(file_path, output_dir=...).
Saída em disco O mesmo run() grava, no diretório do run: canonical.json, semantic.json, enriched.json e report.md.

Neste modo não há fila: arquivo local → pipeline → artefatos em runs/… (ou pasta indicada por -o).

Fluxo 2 — Worker SQS

Diagrama lógico

Fila entrada (SQS) │ ReceiveMessage (Body) ▼ worker.py → adapters/aws/sqs_worker.py (run_forever / process_one_message) │ ├─► domain/messages.py (parse_input_message → InputJob) │ ├─► adapters/aws/s3_source.py (download_object_to_tempfile) │ │ │ └──► S3 (bucket + key) │ ├─► orchestrator/pipeline.py (run em diretório temporário) │ ├─► domain/report_sections.py + domain/messages.py │ (Markdown do relatório → objeto report por seções + metadados) │ └─► SQS saída (SendMessage JSON) → DeleteMessage na fila de entrada (após envio bem-sucedido)

1) Ponto de entrada do processo

  • project/worker.py — chama run_forever() do módulo SQS.
  • Script instalável (se o pacote estiver instalado em modo editável): iadt-worker (definido no project/pyproject.toml).

2) Configuração

project/config/settings.py — variáveis de ambiente, entre outras:

  • AWS_REGION
  • IADT_INPUT_QUEUE_URL / IADT_OUTPUT_QUEUE_URL
  • IADT_WORKER_VISIBILITY_TIMEOUT
  • IADT_WORKER_OUTPUT_MAX_BYTES (limite do corpo JSON na saída)

Credenciais AWS vêm do ambiente da máquina ou da role (ECS/Lambda/EC2), não de chaves no código.

3) Loop da fila de entrada

project/adapters/aws/sqs_worker.py — run_forever() cria clientes SQS e S3, faz long polling na URL da fila de entrada e, para cada mensagem, delega a process_one_message().

4) Corpo da mensagem → trabalho normalizado

project/domain/messages.py — parse_input_message(body, fallback_job_id=…) aceita, entre outros:

  • JSON v1 com schema_version, source: { "type": "s3", "bucket", "key" }, job_id opcional;
  • evento no estilo S3 → SQS (Records[0].s3);
  • envelope SNS com string Message contendo um desses JSONs.

O resultado é um InputJob: job_id, correlation_id, source_bucket, source_key.

Se o parse falhar, o worker pode enviar à fila de saída um JSON de falha (build_system_failure_output_v1, estágio parse_input), apagar a mensagem da entrada e seguir (evita reprocessamento infinito de mensagem inválida).

5) Download do diagrama

project/adapters/aws/s3_source.py — download_object_to_tempfile grava o objeto em arquivo temporário com extensão alinhada ao que o pipeline aceita (SUPPORTED_EXTENSIONS em settings).

Se o download falhar → JSON de saída com failure_stage: s3_download → delete na entrada (após envio ok).

6) Pipeline (núcleo compartilhado com o CLI)

Com o arquivo local temporário, o worker chama run(local_path, output_dir=diretório_temporário) para não depender de runs/ persistente.

project/orchestrator/pipeline.py — extração → enriquecimento semântico → análise de risco → geração do relatório em Markdown → validação.

Os títulos obrigatórios das seções do relatório vivem em um único lugar: project/domain/report_layout.py (importado pelo P3 e pelo parser de seções).

Se o pipeline lançar exceção → payload de saída com pipeline_error e estágio de falha apropriado.

7) Markdown → JSON por seções (saída na fila)

project/domain/report_sections.py — divide o texto do relatório pelos cabeçalhos ## N. ….

project/domain/messages.py — build_output_message_v1 monta o JSON v1: status, validation, elapsed_s, objeto report com chaves estáveis (por exemplo executive_summary, identified_components, …).

O LLM continua gerando Markdown internamente; o que vai para a fila de saída é JSON com o corpo de cada seção como string, não anexo de arquivo .md.

8) Limite de tamanho (SQS ~256 KB)

project/domain/messages.py — fit_message_payload reduz o JSON se ultrapassar IADT_WORKER_OUTPUT_MAX_BYTES.

9) Publicação e reconhecimento da mensagem

Após montar o payload: SendMessage na fila de saída; em seguida DeleteMessage na fila de entrada só se o envio (e o delete) tiverem sucesso — se o envio falhar, a mensagem volta após o visibility timeout para nova tentativa.

Testes que documentam o comportamento

  • project/tests/test_report_sections.py — parser de seções (ordem, ausência, limites entre cabeçalhos).
  • project/tests/test_messages.py — parse de entrada, montagem de saída e truncagem.
  • project/tests/test_sqs_worker_unit.py — fluxo do worker com mocks (sem AWS real).

Resumo em uma frase

worker.py chama o loop em sqs_worker, que lê a SQS, interpreta o corpo em messages, baixa o PDF no s3_source, executa pipeline.run, serializa o resultado em JSON com seções em messages/report_sections, envia para a fila de saída e remove a mensagem da entrada após sucesso; o CLI continua chamando pipeline.run diretamente com arquivo local.
